# 研究结论与复刻规格
> 本文的实现架构、目录和验收门槛是本项目建议，不声称等于原作内部源码。历史事实用 [Sxx] 引用，网址见 sources.json。

## 1. 目标不是“有点像的卡牌 RPG”
任务是修复一个已存在的 Unity 工程，使锁定版本的玩法、流程、界面与反馈可被逐项对照验证。先锁定服务区、时期、平台、纵横比、玩法集合，再谈百分比。

必须区分三个数字：
- **范围覆盖率**：约定系统和状态有多少已经实现；未实现的不从分母删除。
- **已实现范围的还原质量**：在原作样本下有多少符合要求。
- **证据覆盖率**：规则有多少来自对应版本证据；未知不能记成通过。

一个“五人战斗非常像”的切片，只能称核心战斗切片，不等于 90% 完整 DC。

## 2. 研究纠偏与可复用资料
SHIFT UP 的公司披露明确区分：DC 使用自研引擎，后来的 NIKKE 使用 Unity。[S01] 这不要求你换引擎；用户可观察的行为才是本项目的兼容目标。

Live2D 官方登记 DC 为 Cubism 2。[S02] 旧 `.moc/.mtn` 运行时资源不能简单当作当前 SDK 的可编辑模型使用；官方转换流程涉及旧源工程数据。[S03] 当前 Unity 骨骼方案先保留，通过适配层隔离。

GitHub 查看器和 Repacker 可以帮助整理已有合法素材、了解格式；不能据此声称拿到了战斗逻辑。[S25][S26] HF 检索未发现此次能够验证为原作战斗公式数据集的资源；这不是“全网绝不存在”的结论。无需先训练一个 AI 模型或搭大型 Agent 平台。

确实存在声称提供客户端、服务端及文档的公开帖子；阅读到的讨论混合了不同版本、源码与简陋模拟器，并没有形成可直接信任的最终版来源。[S30] 若用户另有具备研究/使用权限的源码或本地数据，先记录来源、版本、哈希、构建结果和授权边界，再把实际计算路径作为更强证据。不要下载执行来路不明的服务端包，不要把“帖子标题”列为源码已验证。

## 3. 先冻结 Target Manifest
`templates/target_manifest.json` 中必须明确：
- KR / JP / GL；版本日期或可追溯客户端/录屏版本。
- 要复刻早期体验还是停服前后期内容；各模式对应版本不能混搭。
- 原生屏幕区域、参考画幅、目标设备、是否使用加速/自动战斗。
- 用户提供素材的目录与可用性；剧情/角色资源与框架工作明确分工。

纪念版能帮助还原角色、装备、文本与可见页面；没有战斗功能的页面不能验证战斗时序和伤害结算。之前报告里为 MVP 临时设计的经验、掉率和伤害值一律降级为 DESIGN_PLACEHOLDER，除非补齐独立证据。

## 4. 现有工程审计：保留、修补、隔离、替换
先记录 `ProjectVersion.txt`、包清单与锁文件、渲染管线、输入/UI 系统、场景入口、实际编译错误、当前运行录像、存档样例及 Git 状态。不要擅自升级 Unity、改 URP、换依赖注入或把整个工程迁到 ECS。

每个模块必须给出：真实路径/调用链 → 现状 → 对照差异 → 分类 → 最小修复方案 → 测试。分类：
- REUSE：行为和结构已满足目标；不为了“代码好看”重做。
- REPAIR：局部差异，保留接口/数据。
- ISOLATE：短期可用但耦合过强，先加适配层。
- REPLACE：明确测试证明核心假设错误，再替换最小边界。

对“战斗核心完全是回合制”“所有技能共享一个 CD”“动画结束才扣血”等结构性问题，可能必须替换；这只是审计准则，不代表已发现你的工程存在这些问题。

## 5. 战斗核心应当怎样分层
建议链路：
```text
用户内容/版本化数据
  → 数据校验与数值解析器
  → 纯 C# BattleCore
      Commands / Clocks / Scheduler / Targeting / Effects / Formulas / ModePolicy
  → BattleEvent 事件流
  → UGUI + 动效/VFX + 声音 + CharacterPresentation
  → 战斗结果事务 → 背包、养成与存档
```
BattleCore 不依赖 MonoBehaviour、Animator、粒子回调、场景查找或真实网络。可从已有代码逐步抽离，不能为了满足目录图而全仓重构。

定义按 tick、阶段、序号排序的命令和事件。固定 tick 是实现选择，不是原作引擎事实；60Hz 只是可选初始实现，最终按录屏分辨率和稳定性校准。战斗快进通过模式时钟策略控制，不靠把全部系统的 `Time.timeScale` 盲目改成相同值。

### 五类动作分开
早期实机指南区分自动基础攻击、点击技能、上滑技能、Drive 与 Fever。[S04] 这五类不能当作“同一技能按钮换倍率”。

必须有独立状态：存活、可选目标、充能中、技能就绪、行动预约、施放中、Slide 冷却、受控、Drive 选择、QTE、Fever、结算。哪些可同时存在应通过多个状态域表达，不能强塞一个互斥 enum。

### 至少分开这些时钟
基础自动攻击间隔；技能充能；Slide 冷却；状态持续时间；周期触发；关卡倒计时；Drive/QTE；Fever 窗口；UI 实时时钟。

例如睡眠实验对充能和 Slide 冷却给出不同结果。[S14] 这说明“一个状态让整名角色所有进度一起停住”不是可靠的默认。

Drive 的选择、预约、演出、QTE 评价、实际伤害、Fever 积累是不同事件。Fever 的可输入窗口、连点节流、自动操作速度、目标重选、伤害分支、结束条件分别配置。早期资料中的持续秒数或评价充能量仅作为对应版本证据，不能直接用于晚期目标服。[S04]

### 目标与效果执行器
用户负责具体角色技能，但引擎要负责技能语义。为每个效果明确：
- 目标按绝对 HP / HP 比例 / 攻击排行 / 指定属性 / 前后排 / 随机选择；数量与是否可重复；平局处理。
- 排名取施放时快照还是每次命中重新计算；嘲讽和不可选目标的优先级。
- 每段伤害、追加效果、每目标/每命中概率、驱散、抵抗、免疫、护盾、反射、吸血、复活等结算顺序。
- 时间型、行动型和受击型触发不同。官方指南举出的毒涉及行动和受击触发，不能全部写成每秒扣血。[S19]
- 堆叠、刷新、替换、上限、来源与驱散标签；递归触发设置防循环预算。

使用版本化的效果操作码与强类型参数，不在技能中塞任意脚本；未实现操作码必须报错，不能静默忽略。真实角色表由用户补，开发测试使用明确标记的合成测试角色。

## 6. 完整玩法框架，不只是主线
以下是待核对并冻结的功能清单，不能把名字列出来就算完成。早期模式依据 [S04]，World Boss 依据 [S17][S18]，后期内容需进一步匹配目标版本。

| 子系统 | 可复用核心 | 需要单独验证的部分 |
|---|---|---|
| 主线/活动关卡 | 多波次战斗、队伍、奖励事务 | 入场成本、星级、失败/退出、关卡跳转 |
| 日常资源关 | 同一 BattleCore | 次数、难度、日切、各资源表 |
| Underground | 战斗与存档 | 跨节点 HP/死亡/队伍状态如何延续及重置 |
| Devil Rumble | 对手快照、AI | 目标服阵容规则、胜负、计分；离线模拟不可声称真实排名 |
| Narrative | 关卡与活动数据 | 进度、活动货币、商店、重复奖励 |
| Ragna / Ragna Burst（按版本） | Boss 战与贡献记录 | 多次挑战进度、支援、门票、计时、结算；不能只改 HP |
| World Boss | 可变编队的 BattleCore | 官方 20 人、前后排、自动战斗、Drive 顺序以及模式专属规则 |
| Rebirth | 模式政策接口 | 特殊限制/商店/奖励；依据官方指南补齐 [S22] |
| Endless Duel（若目标有） | 批次对战/阵容规则 | 具体队伍限制、连续战及积分，要额外取证 |
| 召唤/收集 | 本地随机抽样、图鉴、重复物处理 | 概率与保底以目标期表为准；没证据不可伪称原版概率 |
| 日常/任务/活动 | 可控日历、进度状态机 | 日切、领取幂等、活动轮换；可离线模拟服务器时间 |

第一阶段展示五人阵容，但战斗数据结构从开始就允许可变人数、前后排、不同 AI/目标政策。World Boss 官方配置是 20 人而非五人 Boss 换皮。[S17][S18]

### 养成与数值来源
独立保存角色固有成长、等级、稀有度进化、突破、觉醒/好感、装备、Soul Carta、点火及增幅属性。各语言术语用映射表，不要把 Awakening、Evolution、Uncap 合成“升级”。Ignition 属后期系统，官方实装记录见 [S21]。

可导入用户资料中已有的表格/JSON，字段缺失必须报告。经验曲线、消耗、掉落、敌人数值、等级开放条件不要套通用指数公式冒充原作。

### 存档与经济
离线优先不等于随便 Save。装备实例与角色实例分开；锁定/收藏/上阵对象不能被材料消耗；战斗奖励使用唯一事务 ID；中断恢复不重复扣票或领奖；原子存档、备份、schema 版本迁移、坏档恢复、随机种子与抽样状态均可测。不要先建账号服、支付或伪实时多人匹配。

## 7. UI：做“参考复原”，不是让 AI 自由设计
原作的历史截图呈现角色占据主体、边缘密集信息、富有识别性的战斗头像操作区、醒目的文字伤害与 Fever 表现。[S02][S04] 同时代原生截图才可测量坐标；营销拼图不能用于还原精确位置。

首批参考状态至少覆盖：
Home、角色列表/筛选、角色详情、养成入口、编队/Leader、关卡选择、队伍确认、战斗空闲、充能就绪、Tap、Slide、Drive 选择、QTE、Fever、受控、死亡/换波、结算、掉落、装备/Soul Carta 页面。World Boss 20 人页面单列。

为每个页面保存参考 ID、服务区/日期、画面内容区、归一化位置、锚点、层级、遮罩、字号比例、描边、切片边框、点按热区、弹窗与返回路径。测量未知就留空，不写假坐标。

先复原大轮廓和信息层级，再做字体/边角/图标，最后做交互状态。禁止将 UI 改造成通用圆角 Dashboard、现代 SaaS 面板或另一款手游风格。用户立绘暂缺时可遮罩该区域测 UI，但必须同时报告遮罩面积，不能据此声称整屏美术 90%。

## 8. 动效、VFX、声音：必须有“逐帧事件表”
每个操作制作 cue sheet：输入帧 → 前摇 → 冲击帧 → 伤害显示 → 恢复 → 下个可输入帧。记录帧率、视频是否变速、缺帧、时钟、缓动、缩放、旋转、透明度、层级、音效起点及可否跳过。

优先复原：点按反馈、头像充能/就绪、上滑拖拽、暴击提示、伤害数字轨迹、命中闪白、受击扰动、Drive 切入/QTE、Fever 启停、换波、结算奖励。不要用统一屏震加彩色粒子替代这些区别。

技能专属美术可由用户提供，框架需支持不同命中数量和时间点、屏幕级/目标级效果、文字特效、语音优先级、音效重叠限制、音乐 ducking、自动模式和跳过策略。界面动效走 UI 时钟，不能因为战斗暂停把 QTE 按钮也冻死。

### 动态角色方案
定义 `ICharacterPresentation`：设置资源/皮肤、播放表现事件、表情、注视、暂停/速度、销毁清理。实现 Static / NativeSkeleton / Cubism 三个适配器中的需要项。业务只依赖接口。

先选一名用户提供且有权使用的代表角色，对比呼吸、眨眼、头发、脸部变形与触摸反应。骨骼方案若达不到需要的面部/网格表现，再评估 Cubism。不要在立绘尚未确定时重绑全部角色，更不要把伤害触发绑在某种动画格式上。

## 9. 实际工程自动化
现有 Unity 自动化桥优先。没有时可评估 CoplayDev Unity MCP，先验证本工程兼容性并锁定版本，再使用其真实暴露的场景、日志、测试、截屏接口。[S27] 本包没有在你的电脑安装或连接此工具。

只有一个集成代理控制活动 Unity 编辑器。其余代理处理独立 C#、数据、测试和文档。编辑器任务提交成功不等于任务完成；必须取得测试结果文件、运行日志和实际截图。无法获得这些证据就标记 BLOCKED，不能编造通过。
